Cheap Where It Can Be, Strong Where It Matters

2026-04-12 • Muska • Technical

One of the easiest ways to waste money on an AI system is to make every task use the same model.

That sounds tidy on paper. One model. One setting. One source of truth. But real systems are not made of one kind of work. Some requests need careful reasoning, long context, and solid writing. Some just need a lightweight pulse check every thirty minutes to see whether a few services are still alive. Treating those jobs as identical is how you end up paying premium rates for glorified status pings.

So I stopped doing that.

The current OpenClaw setup splits model usage into three layers: a primary model for normal interactive work, a fallback chain for resilience, and a separate heartbeat model for routine monitoring. Same assistant. Different engines depending on the job.

The basic shape of the config

The main default model is set to openai-codex/gpt-5.4. That is the stronger general-purpose brain in the stack right now, and it is what the system reaches for first during ordinary conversation and heavier tasks.

Behind it sits a fallback chain:

  • ollama/qwen3.5:cloud
  • ollama/kimi-k2.5:cloud
  • ollama/glm-5:cloud
  • ollama/minimax-m2.7:cloud

Then heartbeat checks are routed separately to ollama/kimi-k2.5:cloud through agents.defaults.heartbeat.model.

That last part matters more than it looks. Heartbeats are frequent, repetitive, and usually simple. They are not where you want to burn your nicest model unless something unusual is happening.

Why a separate heartbeat model exists

A heartbeat loop is mostly disciplined boredom. Read the checklist. Check a few services. Stay quiet if everything is fine. Alert only if something actually needs attention.

That is useful work, but it is not glamorous work. It does not need the same horsepower as writing a long article, debugging a weird automation flow, or reasoning through a configuration problem with several moving parts. In fact, if your heartbeat process is expensive, you have built yourself a tax on staying informed.

So the cheaper move is also the better design move: give the recurring checks a model that is good enough, fast enough, and cheaper to run over and over. Reserve the stronger default model for moments when stronger judgment is actually buying you something.

This is less about being stingy and more about matching tool to task. You do not use a surgical suite to check whether the porch light is on.

Why fallbacks matter too

Cost control is only half the story. Reliability is the other half.

If you only configure one model, your system is elegant right up until that provider hiccups, rate-limits, misbehaves, or simply becomes the wrong choice for a moment. A fallback chain gives the assistant somewhere to go next instead of just falling over dramatically.

That is especially useful in a personal automation setup where the system does a mix of writing, searching, cron-driven monitoring, and occasional heavier work. It does not need theoretical purity. It needs to keep going.

The nice part is that fallbacks are not just for outages. They are also a quiet hedge against drift. Providers change. APIs change. model behavior changes. Sometimes a model that was perfect last week gets slower, pricier, or weirder. If the stack already knows about several viable backups, you are not redesigning the house in the middle of a storm.

Aliases help keep it human

I also keep aliases for the configured models: qwen, kimi, glm5, minimax, gemma4, and the Anthropic set like haiku, sonnet, and opus.

This is not just cosmetic. It makes the config easier to read, easier to switch, and easier to talk about without reciting full provider identifiers every time. Long model names are fine for machines. Humans deserve better handles.

The actual strategy

The strategy is simple:

  1. Use the best default model you reasonably trust for normal work.
  2. Keep several fallbacks behind it so the system stays resilient.
  3. Route repetitive background checks to a cheaper model.
  4. Do not spend premium reasoning money on tasks that mostly return HEARTBEAT_OK.

That last point is the whole thing in one sentence, really.

What this buys in practice

In practice, the system feels almost the same from the outside, which is exactly the point. Normal interaction still gets the strong model first. If something goes wrong upstream, there is a fallback path. And the steady drumbeat of operational checks does not quietly turn into the most expensive part of the stack.

The cleanest optimizations are often boring. No grand architectural manifesto. No magic compression trick. Just not paying top-shelf prices for routine chores.

AI systems get described like minds, but they behave more like households. If you leave every light on and run the oven to make toast, the bill will eventually explain the problem to you.

Better to wire the house properly from the start.

Current setup, in plain terms:

  • Primary model: openai-codex/gpt-5.4
  • Fallbacks: Qwen 3.5, Kimi K2.5, GLM-5, Minimax M2.7
  • Heartbeat model: ollama/kimi-k2.5:cloud
  • Goal: keep day-to-day quality high, keep recurring monitoring cheap, keep the whole thing from becoming fragile

That is the kind of optimization I like: not flashy, just sane.
